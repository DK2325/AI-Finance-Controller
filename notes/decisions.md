## Phase 0 — Foundation (22 Aug 2026)

### Repo root is flat

The repo root *is* `AI Finance Controller/`. Packages sit directly inside it rather than
under a nested `ledgerloop/` project folder. The Python package and the CLI keep the name
`ledgerloop`.

**Rejected:** a nested `ledgerloop/` directory, which would have matched BUILD.md's
layout diagram literally but buried every path one level deeper for no gain.

### Compose project name is pinned

`docker-compose.yml` sets `name: ledgerloop` explicitly.

Compose otherwise derives its project name from the containing directory, and
`AI Finance Controller` is not a legal project name — spaces and capitals. Without the
pin, `docker compose up` fails on this machine and on any reviewer's clone that keeps the
folder name. This is a one-line fix that would have been a confusing failure on 4 Sept.

### Shared infrastructure lives in `ledgerloop/`, not in a quarantined package

`ledgerloop/` holds the CLI, config, engine/session, the SQLAlchemy models and the Alembic
migrations. `core/`, `model/`, `llm/` and `api/` all import from it.

This does not weaken the isolation boundary: the boundary forbids importing `datagen/` and
reading the answer key, and `ledgerloop/` does neither. Putting the schema anywhere else
would have meant either duplicating it or letting `api/` own it, and `api/` is downstream
of the matcher.

### `audit_records` is append-only at the database, not only in code

BUILD.md asks for no UPDATE or DELETE path in application code. That is a promise about
code review. A `BEFORE UPDATE OR DELETE` trigger that raises is a guarantee, and it holds
against anyone reaching past the ORM with raw SQL.

Verified in Phase 0 by inserting a record, then attempting both an `UPDATE` and a `DELETE`
over `psql`: both rejected, row unchanged.

**Cost:** ~20 lines of migration, and dev data cannot be tidied away — the Phase 0 probe
row is permanent in any database it was written to. That is the correct trade for a
financial control, and wiping the volume is the dev escape hatch.

**Rejected:** `REVOKE UPDATE, DELETE` on the table. Cleaner-looking, but it is bypassed by
any superuser connection, and the demo connects as the owning role.

### Migration 0001 was autogenerated against a live Postgres, not hand-written

Hand-writing the initial migration invites silent drift from `models.py`. It was generated
with `alembic revision --autogenerate` against a running `db` service, then the trigger was
appended by hand. The autogenerated body and the models are therefore identical by
construction.

### Alembic runs on every container start

`docker/entrypoint.sh` runs `alembic upgrade head` before `uvicorn`. `upgrade head` on an
already-current database is a no-op, so this is idempotent — verified by running it twice.

**Rejected:** a separate one-shot `migrate` service. More moving parts in Compose, and it
reintroduces the ordering problem the healthcheck already solves.

### `web/` is a dependency-free placeholder

Phase 0's `web` service is a ~25-line Node script using only the standard library, serving
one static page. The real Next.js + Tailwind + shadcn/ui frontend is Phase 6 scope.

The point is that `docker compose up` must never block on an `npm install` while the stack
is still being proven. Flagged here so it is not mistaken for an unfinished frontend.

### `.gitattributes` forces LF on shell scripts

`docker/entrypoint.sh` must have LF endings or the Linux container cannot execute it. On a
Windows checkout git would happily convert it to CRLF and produce an error message
(`exec format error`) that says nothing about line endings.

### Deviation: `uv` was not used

BUILD.md names `uv` in the stack. The project uses a plain `venv` plus `pip`, because a
working venv already existed and swapping tooling mid-setup buys nothing here.
`pyproject.toml` is the source of truth; `requirements.txt` mirrors it for the Docker build.

If `uv` is wanted later it is a drop-in — the dependency list is already declarative.

### Deviation: `--exclude-cases` is not on the CLI yet

Phase 1 requires `generate --exclude-cases tds_deducted,refund_netted` for the held-out
design. The Phase 0 skeleton registers only the flags in BUILD.md's canonical CLI block,
to stay inside phase scope. It lands in Phase 1.

## Pre-decision for Phase 5 — LLM provider (recorded 22 Aug 2026)

Intended provider is **NVIDIA NIM**, model `nvidia/nemotron-3-super-120b-a12b`
(hybrid Mamba-Transformer MoE, 124B total / ~12B active, 1M context, reasoning-capable).

```
from openai import OpenAI
client = OpenAI(base_url="https://integrate.api.nvidia.com/v1", api_key=NVIDIA_API_KEY)
```

Not yet implemented — Phase 5 scope. Recorded now so the phase is planned against the
right constraints.

**What this changes:** the SDK becomes `openai` rather than `anthropic`; `.env.example`
gains `NVIDIA_API_KEY`. Nothing architectural: BUILD.md's LLM rules are provider-agnostic
and every one of them still holds.

**What it does not change:** the LLM still never decides a match. Still Pydantic-validated
with one retry then the exception queue. Still versioned prompts referenced by version in
the audit record. `--mock-llm` still carries Phases 1-4.

**Constraints to design around, flagged now rather than discovered in Phase 5:**

1.  *The free prototype endpoint is rate-limited.* Phase 7 wants a 25,000-row run with
    measured throughput. Only the residue (~15% of rows) reaches the LLM, but that is
    still thousands of calls. The exception layer needs concurrency control and backoff,
    and the throughput number must state whether it was endpoint-bound or compute-bound.
    Reporting a rate-limited number as if it were a system limit would be dishonest.

2.  *Free means the "cost per 1,000 rows in rupees" metric degenerates to zero.* Zero is
    not a useful input to the Phase 7 unit-economics paragraph. Report measured token
    counts as the primary figure, plus a priced equivalent at a stated public rate, and
    say which is which.

3.  *Reasoning mode* (`extra_body={"chat_template_kwargs":{"enable_thinking":True}}`)
    emits a thinking trace. The parser must not mistake reasoning text for the payload,
    and thinking tokens inflate both latency and token cost. Measure with it on and off
    before committing.

4.  *Structured-output support needs verifying, not assuming.* If the endpoint honours
    `response_format` with a JSON schema, use it. If not, fall back to prompt-plus-Pydantic
    with one retry, which BUILD.md mandates anyway. Either way the schema-validation
    failure rate is a reported Phase 5 metric, so a weak result shows up as evidence.

5.  *The endpoint logs usage and warns against uploading confidential data.* Irrelevant
    here and worth saying out loud at the panel: every record in this system is
    synthetic, by construction. The isolation boundary means the demo never has real
    merchant data to leak. This must stay true - never point this pipeline at a real
    settlement file.
